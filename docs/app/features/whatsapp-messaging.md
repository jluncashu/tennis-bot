# What it does

- `GET /webhook` — Meta's verification handshake. Echoes back
  `hub.challenge` if `hub.verify_token` matches `WHATSAPP_VERIFY_TOKEN`,
  otherwise `403`.
- `POST /webhook` — receives an incoming message event. Responds `200`
  immediately (Meta retries on timeout/non-2xx), then extracts the first
  message from `entry[0].changes[0].value.messages[0]`:
  - `type: "interactive"` with `interactive.type: "list_reply"` — a tap on
    a row of any of the three picker lists — is routed to `handleListReply`
    (`packages/api/src/services/conversation.service.ts`), which dispatches
    on the row id's prefix: `nav:week:<offset>` re-sends the day list for a
    different week, `date:<yyyy-mm-dd>` sends the time-slot list,
    `slot:<date>:<hour>` sends the court list, and
    `court:<date>:<hour>:<covered|uncovered>:<n>` acknowledges the full
    selection.
  - Otherwise, if the message has `text`, it's routed to
    `handleIncomingMessage`: a greeting (`hi`/`hello`/`book`, case-insensitive)
    sends the day-picker list for the current week (offset `0`). Any other
    text is ignored.
  - Anything else (status updates, unsupported message types) is ignored
    after the ack.

The picker is three separate plain WhatsApp **list messages** (`sendList`),
sent one after another as the user taps through — not the WhatsApp Flow.
See [court-booking-flow.md](court-booking-flow.md) for the separate,
currently-untriggered Flow-based booking UI (`POST /flow`, its own
multi-screen day/slot/field/confirm flow). The two are independent
booking UIs; only the list-message one is currently wired to the live
webhook.

There is no server-side session — each step encodes everything picked so
far into the next message's row ids, and the following step just parses
it back out of the tapped id. Nothing is persisted until the final
acknowledgement (see Known gaps).

## Step 1 — day, with week navigation

`sendWeekPicker(phone, weekOffset)` builds a list with two sections:

- **Available days** — 7 rows for the selected week, ids `date:<yyyy-mm-dd>`,
  generated by `getWeekDays(weekOffset)` (`today + weekOffset*7 + i` days).
- **Navigate** — a `Next week ▶` row (`nav:week:<weekOffset + 1>`) always
  present, plus a `◀ Previous week` row (`nav:week:<weekOffset - 1>`) only
  when `weekOffset > 0` — so the current week (offset `0`) only offers
  "next", matching WhatsApp's own conversation-window semantics of not
  booking into the past.

Tapping a nav row re-sends the list for the target week. Tapping a date
row moves to step 2.

## Step 2 — time slot

`sendSlotPicker(phone, date)` sends one section, **Available times**, with
one row per 2-hour frame from `OPEN_HOUR` (8) to `CLOSE_HOUR` (22) — 7 rows,
ids `slot:<date>:<startHour>`. Frames are 2 hours (not 1) purely to stay
under WhatsApp's 10-row-per-list cap — 14 hourly slots wouldn't fit.
Availability isn't checked against anything; every frame is always shown.

## Step 3 — court

`sendCourtPicker(phone, date, hour)` sends two sections: **Covered courts**
(`COVERED_COURTS` = 4 rows) and **Uncovered courts** (`UNCOVERED_COURTS` =
1 row), ids `court:<date>:<hour>:<covered|uncovered>:<n>`. Tapping a court
row is the terminal step — `handleListReply` acknowledges the full
selection via `sendText`. Nothing is written anywhere; there's no
reservations table yet (see Known gaps).

# Interactions

Outbound replies go through the WhatsApp Cloud Graph API
(`https://graph.facebook.com/v20.0/<phone-number-id>/messages`). See
[Architecture](/architecture.md) for the full picture.

# Config

Requires `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`,
`WHATSAPP_VERIFY_TOKEN`, validated in `packages/api/src/config/env.ts`.

# Known gaps

- Nothing is persisted — the final `sendText` acknowledgement is the whole
  effect of completing the picker. There's no reservations table yet and
  no check that the picked time/court is actually free; every slot and
  court is always shown as available. The Flow-based path
  (`court-booking-flow.md`) has the same mock-only limitation.
- New-conversation detection (`registerIncomingMessage`/`contacts` table)
  and the `"Intro"` message are not wired into the live `receiveMessage`
  handler — the code exists but is unreachable (commented out).
- The `contacts` module has no `.test.ts` — this repo doesn't have a test
  runner (vitest) set up yet, so it was skipped rather than added as a
  side effect of a feature.
- No error surfaced to the sender if `sendText`/`sendList` fails (only
  logged).
- No upper bound on how far into the future "Next week" can go.
- Time slots are fixed 2-hour frames (8-10, 10-12, ... 20-22) — courser
  granularity than the Flow-based path's 1-hour slots, a tradeoff for
  staying under WhatsApp's 10-row list cap.
